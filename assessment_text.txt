6. Technical Discussion Points
6.1 Dynamic Algorithm Parameters
Recommendation: Use a JSON-based metadata-driven parameter system. Instead of hardcoding every algorithm parameter directly in the WPF UI, the application can read 
a structured JSON parameter definition and dynamically generate the required controls. This approach keeps the UI and algorithm configuration loosely coupled and reduces 
repeated UI-side code changes when parameters are added, removed, renamed, grouped or modified.

The JSON file should define parameter name, display name, group/category, data type, default value, min/max range, unit, description/help text, visibility, basic/advanced 
flag, UI control type and validation rules.

Parameter groups can be organized logically such as Bump Parameters, Void Parameters, Layer Parameters, Deep Learning Enhancement, GPU Settings and Output 
Settings.

The same metadata can drive UI generation, validation, default/reset behavior, save/reload behavior and tooltip/help text.

This reduces mismatch risk between algorithm-side parameters and UI-side controls and makes future algorithm updates easier to deploy.
Example JSON definition:
{
  "group": "Void Parameters",
  "parameters": [
    {
      "name": "VOID_MIN_AREA",
      "displayName": "Void Min Area",
      "type": "double",
      "default": 15.0,
      "min": 0.0,
      "max": 5000.0,
      "unit": "um2",
      "control": "numeric",
      "description": "Minimum void area used for filtering small noise regions.",
      "visible": true,
      "advanced": false
    },
    {

This approach works well for normal algorithm parameters such as thresholds, numeric values, flags, paths and enum options. If a new parameter requires a special visualization, custom

6.2 Deep Learning Model Deployment
Recommendation: Use a dedicated DLL/API wrapper for inference rather than executing Python scripts directly from the WPF application. Python scripts are useful during 
R&D and model validation, but for production integration, a wrapper-based approach provides better performance control, cleaner deployment, stable application integration 
and improved maintainability.
Approach
Assessment
Direct Python script execution
Useful for R&D, model validation and prototype testing. Not recommended as the final production 
integration approach because deployment, dependency control and error handling become harder.
DLL/API inference wrapper
Recommended for production integration. Provides a stable interface between the WPF application 
and the model, improves performance control, simplifies deployment and keeps model details 
isolated from the main application.
Practical transition approach
Continue using scripts during model development and validation. Move to wrapper-based 
deployment for final application integration.
Suggested wrapper interface:
Initialize(modelConfigPath, gpuDeviceId)
EnhanceVolume(inputPath, outputPath, progressCallback)
GetStatus()
Cancel()
Release()

The WPF application should call stable wrapper methods such as Initialize, EnhanceVolume, GetStatus, Cancel and Release.

Model-specific details such as preprocessing, patch size, overlap, batch size, runtime selection, GPU device ID, TensorRT cache path and post-processing should be 
handled through a separate model configuration file.

For large HBM volume data, the inference layer should support chunk/tile-based processing, GPU memory validation, progress reporting, cancellation, model-version 
checking and clear error/status reporting.

This keeps the main application independent from frequent model-side changes and makes future model updates easier to deploy.
Example model configuration:
{
  "modelName": "HBM_Enhancement",
  "modelVersion": "1.0.0",
  "runtime": "TensorRT",
  "inputType": "uint8",
  "outputType": "uint8",
  "patchSize": [512, 512, 64],
